# 资源聚合与链接检测设计（草案）

> 状态：**思路记录 + 待决策**，还未动手写代码。
> 目标：把「网盘资源从哪来、怎么入库、怎么判活死」做成**可插拔、解耦、带开关**的架构，
> 不重蹈老项目「说啥写啥、越堆越乱」的覆辙。配合 `docs/重做设计方案.md` 的域划分（本特性属 `content` 域）。

## 0. 一句话概括

**来源即插件**：pansou、gying（自写）、人工录入、其他站点……都只是「一个来源」，
统一吐出规范化的候选链接 → 识别归属影片 → 去重/更新入库 → 用户访问时**顺带惰性检测**有效性。
每个环节独立、可开关、可替换。

---

## 1. 用户的原始思路（原样记录）

1. **pansou 只是一个来源**。gying 到时候自己写，还有人工录入等各种来源，
   **像插件一样插入我的网站和表**。
2. **检测放在用户使用/获取的时候**做，让返回快一点；用户访问时**顺带检测**，
   不需要另外单独跑一遍检测。
3. **搜索结果要入库**；入库要**去重**；并且 **note 要更新**——
   同一个链接 note 变了，大概率是**更新了集数**，所以 note 要跟着更新。
4. 代码要**有规划、可插拔、解耦、有开关**，不要像老项目那样随意堆。

## 2. 架构：四阶段流水线（各自解耦、可开关、可替换）

```
[Source 来源插件]  →  [Matcher 识别归属]  →  [Ingestor 入库]  →  [Checker 惰性检测]
   pansou             TMDB / 豆瓣 / 标题匹配     去重 / note更新 / 状态判定    用户访问时按需
   gying(自写)                                                              读旧值秒回+后台刷新
   人工录入
   其它站点
```

**关键：四个阶段是四个独立接口，互不耦合，各有开关。** 一次只把一个阶段做到底。

### 2.1 Source（来源插件）—— 只负责"找链接"
- 职责：给定关键词 / 定时任务，产出一批**规范化候选** `RawLink`，**不关心归属哪部片、也不入库**。
- 契约（草案）：
  ```
  RawLink {
    panType        // baidu/quark/xunlei/magnet/...
    url            // 分享链接
    password       // 提取码（可空）
    note           // 资源标题/说明（含"全40集/1080P/合集"等信息）
    source         // pansou / gying / manual / xxx
    sourceItemId   // 来源内唯一 id（去重/幂等用，可空）
    publishedAt    // 来源发布时间（可空）
    rawTitle       // 原始标题（供 Matcher 匹配）
    images         // 海报图（可空）
  }
  ```
- 插件注册：每个来源一个实现，Spring 里按开关装配；新增来源 = 加一个实现，不动其它代码。
- 已有可复用：pansou 的 `/api/search`（已部署，内部 `http://pansou`）。

### 2.2 Matcher（识别归属）—— 把候选映射到某部 media
- 职责：用 `rawTitle` / 年份 去 TMDB / 豆瓣 / 本地库匹配出 `mediaId`（含置信度）。
- **和 Source 解耦**：Source 不做识别，Matcher 独立可换。
- 匹配不到 → 不硬塞，进「待认领/需求池」（记录需求热度，供人工或后续补匹配）。

### 2.3 Ingestor（入库）—— 去重 / note 更新 / 状态判定
- 职责：把 `(mediaId, RawLink)` 落到 `media_link`，**幂等 upsert**。
- 复用已有门槛：`MediaLinkAdFilter`（广告过滤）、`SensitiveWordService`（敏感词）、
  `MediaLinkRelevance`（相关性打分，防张冠李戴）、`MediaLinkUrlNormalizer`（URL 规范化）。
- 去重与 note 规则见 §4。

### 2.4 Checker（惰性检测）—— 用户访问时顺带、不阻塞
- 职责：判断链接活死（baidu/quark/xunlei）+ 磁力做种（弱信号）。
- **核心：读旧值秒回 + 后台异步刷新**，绝不同步现查拖慢页面。见 §5。
- 检测逻辑移植自 pansou `check_service.go`（我已通读），只做 baidu/quark/xunlei/magnet。

## 3. 数据模型改动（草案）

### 3.1 `media_link` 增列（检测结果）
| 列 | 说明 |
|---|---|
| `check_state` | ok / bad / locked / unsupported / uncertain（未检为 null） |
| `checked_at` | 上次检测时间；配合 TTL 判断是否需刷新 |
| `check_summary` | 检测说明（"链接有效"/"已取消分享"…），可选 |
| `share_id` | 规范化分享 id（去重键的一部分，见 §4） |
| `last_seen_at` | 来源里最近一次仍出现的时间（新鲜度） |

> `invalid` 沿用：`check_state=bad` 时置 `invalid=1`，前台不展示但**不硬删**（保留记忆）。

### 3.2 结构化解析字段 —— **已决策：不做**
- note 集数/清晰度难统一，放弃结构化。note 更新用"较新覆盖"（§4.5）。

### 3.3 队列（异步基建）—— **暂缓，先不做**
- 队列本是给"用户搜了库里没有的片 → 后台去采集、不让用户干等"用的异步缓冲。
- 当前模型「采集单独跑（定时/手动）+ 检测在转存点击时」，**用户请求不等采集**，故现在不需要。
- 以后要做"搜不到即实时补录"时再引入（DB 表 `backfill_queue` 或 Redis list）。

### 3.4 检测全局缓存
- Redis，key = `normalized(panType+shareId)`，**跨 media/跨用户共享**（热门链接只查一次）。
- TTL 按状态（抄 pansou）：`ok 24h / locked 12h / bad 6h / unsupported 24h / uncertain 30min`。

## 4. 去重与 note 更新规则（**重点：大数据量下的性能**）

> 现状：`media_link` **当前没有任何去重**（只有非唯一索引 `idx_media_status`、`idx_pan`，无唯一键、
> 入库无去重逻辑）。以下为要新建的方案。

### 4.1 去重键：`media_id + pan_type + share_id`
- **绝不能用原始 URL 去重**：同一分享有 `?pwd=`、域名差异（alipan/aliyundrive）、多行提取码等，
  且 `url` 是 `VARCHAR(1024)`，**长字段无法建高效索引**。
- 新增 **`share_id`** 列（短、可索引），由 URL 确定性提取：
  | 网盘 | share_id 提取 |
  |---|---|
  | quark | 路径 `/s/{id}` 的 id |
  | baidu | `surl`（`/s/` 后去掉前导 `1`） |
  | xunlei | `/s/{id}` 的 id |
  | magnet | btih infohash（统一转 40 位小写十六进制） |
  | 其它(aliyun/uc/123/tianyi) | 路径最后一段 |
  | 兜底 | 提取不到时用 `md5(规范化URL)` 32 位 |
- **提取逻辑集中在一个工具类**（`ShareIdExtractor`），入库和查询用同一份，保证一致。
- **跨来源天然合并**：pansou 与 gying 找到同一条 → 同一个 share_id → 同一行（`source` 记来源）。

### 4.2 落库方式：唯一键 + `INSERT ... ON DUPLICATE KEY UPDATE`（**性能关键**）
- 加唯一键：`UNIQUE KEY uk_link (media_id, pan_type, share_id)`。
  - `share_id` 用 **`VARCHAR(64) CHARACTER SET ascii`**（share_id 都是 ascii），
    让索引更小、更快；`pan_type` 也是 ascii。键总长 ~ 8+16+64 字节，远低于 InnoDB 3072 上限。
- 入库一律用 **`ON DUPLICATE KEY UPDATE`**（单条原子语句）：
  - 不存在 → 插入；已存在 → 更新 `note`（较新覆盖）、`last_seen_at`、`updated_at`。
  - **不要 SELECT-then-INSERT**：N 次查询 + 并发竞态；唯一键 upsert 一条搞定，且走索引 O(log n)。
- 批量采集用**批量 upsert**（一条 SQL 多 VALUES），减少往返。

### 4.3 数据量大了的性能考量
- **写**：upsert 命中 `uk_link` 唯一索引，百万级也是 O(log n)，不退化。
- **读**（`listForViewer`）：已按 `media_id` 过滤，走 `idx_media_status`；单片链接数有限（几十条），快。
- **不给 `url` 建索引**：它只用于展示。去重/查询只碰短的 `share_id`。
- **检测缓存不落 DB 扫描**：全局缓存 key = `pan_type:share_id`（Redis），热门链接只查一次。
- **软删除不删行**：`invalid=1` 的死链保留（做记忆，防采集复活），查询已过滤 `invalid=0`，
  不影响读性能；行数增长可接受（死链占比可控，必要时定期归档超老的 `invalid=1` 行）。

### 4.4 迁移注意（上唯一键前必须先清历史重复）
- 直接 `ALTER ADD UNIQUE` 会因**存量重复行**失败。迁移步骤：
  1. 加列 `share_id / last_seen_at / check_state / checked_at`；
  2. 回填 `share_id`（按 §4.1 规则，对存量 url 计算）；
  3. **合并存量重复**（同 `media_id+pan_type+share_id` 只留 1 行，其余删）；
  4. 再 `ADD UNIQUE KEY uk_link`。

### 4.5 note 更新（按决策：不结构化，较新覆盖）
- 同一条链接（同 share_id）再次采到、note 不同 → **用采集时间较新者覆盖 note**。
- 不同平台/不同链接 = 不同 share_id = 不同行，各留各的 note，不冲突。
- 极偶尔旧帖回流导致 note 降级 → 下次采集自愈，可接受（不做结构化集数解析）。

## 5. 检测模型（**转存前触发**，非页面加载）

最终采用的模型（比"页面加载惰性检测"更省）：**用户点"转存"时，先检这一条**。

1. **单条实时检测**：用户点转存 → 检这一条 → `ok` 放行转存；`bad` 提示"链接失效"+ 标记，
   用户点下一条。活链接 0.3~1.5s，不卡；只有死链才会等满超时。
2. **只有明确 `bad` 才标失效**（铁规矩，防误杀）：
   `bad`（分享已取消/不存在）→ `invalid=1`（软删除，见 §6）。
   `超时 / uncertain / 网络抖动 / 被风控` → **一律当"未知"，不标失效**，放用户正常点。
3. **结果缓存，一次检测全员复用**：`ok`/`bad` 都存（`check_state + checked_at`，
   并进 Redis，key=`pan_type:share_id`，TTL 抄 pansou：ok 24h / bad 6h …）。
   "很多人点同一条"只会**真查一次**，其余命中缓存。
4. **并发上限 + 每网盘限速**：防止突发把网盘方敲出风控。

> 用户担心的"人多→检测超时→误判失效"：靠 (2) 只对明确 bad 标失效 + (3) 缓存去重 + (4) 限速，
> 三者叠加即可避免误杀。
> 检测能力**自己实现**（借鉴 pansou `check_service.go` 的方法），运行时**不依赖 pansou**。

## 6. 开关与配置矩阵（`jyinshi.*`，语义化）

- `ingest.enabled`：总开关。
- `ingest.source.pansou.enabled` / `...gying.enabled` / ...：每来源开关 + 限速。

- `ingest.auto-approve`：灰度期 = false（自动入库先进 `pending` 人工过一遍），稳了再放开。
- `linkcheck.enabled` / `linkcheck.timeout-ms` / `linkcheck.concurrency`。
- `linkcheck.magnet.scrape` + `trackers`。

## 7. 我的补充（用户让我想的坑与决策点）

- **S1 惰性检测必须异步**：同步现查会把详情页拖到十几秒。方案见 §5。
- **S2 检测缓存全局共享**：按规范化 shareId，热门链接多人开只查一次，防风控。
- **S3 去重用规范化 shareId**，且跨来源去重、唯一索引兜底（§4.1）。
- **S4 note 更新要防降级**：结构化解析集数，"更完整才更新"（§4.2）。
- **S5 来源可信度分级**决定 status：manual=approved；pansou 按置信度 pending/approved。
- **S6 死链不硬删**：bad→invalid=1 保留记忆，避免重复入库，也可复活。
- **S7 幂等再入库**：同一搜索重复跑不产生重复；`last_seen_at` = 新鲜度信号。
- **S8 插件契约要清**：Source 只给 RawLink，识别归属是独立 Matcher，别耦合。
- **S9 复用已有门槛**：`MediaLinkRelevance`/`MediaLinkAdFilter`/`SensitiveWordService` 作准入，防挂错片。
- **S10 异步基建**：队列 + worker，搜索未命中入队，和用户请求解耦（§3.3）。
- **S11 出口 IP 风控**：检测可选走 pansou（已带缓存/代理）或配代理轮换；给并发/限速。
- **S12 可观测**：每来源统计 found/inserted/deduped/dead/uncertain，
  用数据决定"gying 值不值得自写""哪个来源在产垃圾"。
- **S13 磁力语义特殊**：只能给"做种/存活"弱信号，不能判 bad；UDP scrape 从服务器出去未必通，
  **不拿它 gate 入库**。
- **S14 前端呈现**：VO 带 `check_state` 做角标（有效/失效/需提取码/未知）；
  失效的折叠/降权而非直接消失。
- **S15 灰度安全阀**：全局/来源/阶段三级开关 + `auto-approve` 开关，先全人工再放自动。

## 8. 已定决策（拍板，作为实现依据）

1. **直接入库**：自动采集直接 `approved`，不走 pending 灰度。
2. **不结构化**：note 用"较新覆盖"，不解析集数/清晰度。
3. **磁力只校验格式 + 规范化 infohash**，不做 UDP scrape。
4. **检测自己实现 + 自己缓存**（DB `check_state` + Redis），运行时不依赖 pansou，仅借鉴其方法。
5. **死链软删除**（`invalid=1`）而非真删——防采集复活、留记忆。
6. **采集只入库不判死活**；死活只在**转存点击时**判。
7. **只有明确 `bad` 才标 `invalid=1`**；超时/uncertain 当未知，不标失效。
8. **去重**：唯一键 `(media_id, pan_type, share_id)` + `ON DUPLICATE KEY UPDATE`（见 §4）。
9. **队列暂缓**，不做。
10. **gying 后续自写**为一个 Source 插件。

## 9. 分期落地（一次只做一个阶段，保持可编译可运行）

1. **P1 检测能力（独立、最先可用）**：`LinkChecker`（baidu/quark/xunlei/magnet 格式）+
   Redis/DB 缓存 + `media_link` 加 `check_state/checked_at` + **转存前检测**接口
   （`ok` 放行、明确 `bad` 标 `invalid=1`）。不依赖来源，先把检测跑起来。
2. **P2 去重基建 + 入库**：迁移加 `share_id` 唯一键（先清存量重复）+ `ShareIdExtractor` +
   `Ingestor`（`ON DUPLICATE KEY UPDATE`，note 较新覆盖，软删除记忆）。
3. **P3 来源插件**：定义 `Source` 契约，先接 `PansouSource`（+ Matcher 识别归属）。
4. **P4 更多来源**：gying 自写插件、人工录入接入同一 `Ingestor`。
