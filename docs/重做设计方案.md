# 项目重做设计方案（jyinshi-next）

> 本文是新项目的“开工蓝图”。老项目（`../jyinshi`）保持不动，仅复用其中**有价值的数据**，不复用代码。
> 文档目标：拿着它就能直接开干。带 ⚙️ 的是「我先按推荐拍板、你可随时改」的决策。

---

## 0. 一句话定义

> 一个**网盘影视资源聚合平台**：用户搜索影视/资源 → 平台聚合各网盘链接 → 一键转存到用户自己的网盘 → 追剧每日更新。
> 商业模式：**会员订阅制**——先全员免费，结构上预留“会员开关”，将来定月费/年费即可收钱。

---

## 1. 重做要规避的 4 个老问题

这次架构从根上规避它们：

1. **一个目录塞太多 app** → 本次只做「一套后端 + 一个用户前端 + 一个后台」，边界清晰。
2. **重构只做一半（新旧并存）** → 一次性按业务域分模块，不留半拉子。
3. **构建产物/数据/日志混进源码** → `.gitignore` 一开始就配全；产物、数据、缓存、cookie、日志一律不进仓库。
4. **坏掉的嵌套 git 仓库** → 单一仓库，不用 gitlink/子模块；其它独立工具如要保留就各自独立 repo。

---

## 2. 业务域划分（架构主干）

每个域 = 一个独立的包/模块，互不串味。

| 域 | 职责 | 数据来源 |
|---|---|---|
| **identity 用户域** | 注册、登录、用户资料、登录态(JWT) | 全新 |
| **membership 会员域** | 会员状态（到期时间）、权益判断 `isMember()` | 全新 |
| **billing 计费域** | 套餐、订单、支付/卡密、开通续费 | 全新（先留壳，后填） |
| **content 内容域** | 资源库、媒体元数据、榜单、每日更新 | ✅ 复用老数据 |
| **search 搜索域** | 聚合多源搜索（Gying / SeedHub / PanSou / Flowus 等） | 复用逻辑、重组织 |
| **transfer 转存域** | 网盘账号管理 + 一键转存 + 离线任务（百度/夸克/迅雷） | 复用逻辑、重组织 |
| **ops 运营域** | 敏感词、广告过滤、用户投稿、求片 | ✅ 复用老数据 |
| **analytics 统计域** | 行为埋点、转化漏斗、运营看板 | 全新（取代老 analytics 脚本） |
| **admin 后台** | 上述各域的管理界面 + 系统配置开关 | 全新前端 |

## 3. 商业模型（产品决策）

### 3.1 会员订阅制 —— 核心机制

- 每个用户身上挂一个 **`member_expire_at`（会员到期时间）**：
  - 空 / 已过期 → **免费用户**
  - 未来某时刻 → **会员**
- 全系统只通过一个判断 `isMember(user) = member_expire_at > now()` 来区分权益。
- **现阶段：付费墙总开关关闭，`isMember` 视同全员 true，全员免费畅用。**
- 将来收费：① 接支付/卡密，付款成功就把 `member_expire_at` 往后延；② 打开付费墙总开关。**无需重构。**

### 3.2 付费墙划在哪 ⚙️

推荐**按功能卡**（搜索引流、转存变现），这是这类站点最稳的模型：

| 功能 | 免费用户 | 会员 |
|---|---|---|
| 搜索、浏览资源、看详情 | ✅ | ✅ |
| 查看每日更新 / 榜单 | ✅ | ✅ |
| **一键转存到自己网盘** | 🔒 每天 N 次（默认 N=3，可配） | ✅ 不限 |
| **追剧自动更新 / 直链下载** | 🔒 | ✅ |
| 精品/最新资源 | （可选）🔒 | ✅ |

> 说明：转存是真实成本（占用网盘账号、有风控风险），最适合做付费点；搜索免费用于拉新。
> “每天 N 次”这种轻配额用一张 `usage_log` 按天计数即可，不搞复杂等级。
> **现在全部开放**，上表是“将来开关一开”后的形态。

### 3.3 套餐与收款 ⚙️（2026-06-29 更新：已定）

**月卡 / 季卡 / 年卡** 三档，单一会员等级。收款走**第三方发卡平台**（如聚发货），主站**不对接**微信/支付宝。

- 后台生成 `redeem_code` → 导入发卡平台库存 → 用户付款后收卡密 → 回站 `/activate` 核销。
- 卡密可叠加：`member_expire_at = max(now, 现到期) + plan.days`。
- 将来可选：发卡平台 webhook 自动发码（仍非直连支付）。

### 3.4 注册控制 ⚙️

- 注册方式：**用户名 + 密码**（零成本、最快上线；微信/手机号后续作为绑定登录挂上去）。
- **注册开关**（后台可随时切，存系统配置表）：
  - `OPEN` 开放注册
  - `INVITE` 仅邀请码可注册（控量 / 裂变）
  - `CLOSED` 关闭注册（仅后台手动加人）

## 4. 数据模型

### 4.1 新增表（用户/会员/计费/统计）

```sql
-- 用户
user(
  id, username, password_hash, nickname, avatar,
  member_expire_at,        -- 会员到期时间；空/过期=免费
  invite_code,             -- 本人的邀请码
  invited_by,              -- 邀请人 user_id
  status,                  -- 正常/封禁
  created_at, updated_at, last_login_at
)

-- 第三方绑定（微信/手机号，后续用，先建表占位也可后加）
user_oauth(id, user_id, provider, open_id, union_id, created_at)

-- 套餐（想收费时填价格）
plan(id, name, days, price, enabled, sort)

-- 订单 / 卡密
order(id, user_id, plan_id, amount, status, pay_method, paid_at, created_at)
redeem_code(id, code, plan_id, used_by, used_at, expire_at, created_at)

-- 轻配额：按天统计某动作次数（如转存）
usage_log(id, user_id, action, day, count)   -- 唯一键(user_id, action, day)

-- 行为埋点（统计域）
event_log(id, user_id, event, payload_json, ip, ua, created_at)
```

### 4.2 复用老数据（迁移过来）

| 老表 | 复用 | 备注 |
|---|---|---|
| `media_metadata` / `media_similar` | ✅ 强烈 | 影视元数据镜像，省大量第三方 API |
| `resource` | ✅ | 资源库（自有/外部链接） |
| `daily_update` | 🔁 重设计 | 老表带三网盘链；新库改为**薄策展层**（只存 media_id + 排序/上架 + 手动集数），链接落 `media_link(source='self')`，追更态在 `transfer_monitor`（V039/V041，未迁老数据） |
| `ranking` / `ranking_item` / `ranking_snapshot` | ✅ | 榜单历史 |
| `sensitive_word` / `ad_filter_rule` | ✅ | 运营规则 |
| `pan_account` | ⚠️ | 网盘账号，敏感，单独迁、重新加密 |
| `user_contribute` / `user_demand` | ✅ 改造 | 投稿/求片，挂到真实 `user_id` 上 |
| `pan_transfer_record` / `user_transfer_action` | 🔁 重设计 | 并入新 `usage_log` + 转存历史 |
| `search_cache` / `search_log` / `*_api_error` / monitor 运行态 | ❌ | 缓存/日志垃圾，不迁，重新长 |

> 迁移做法：写一个**一次性迁移脚本**，从老库 `SELECT` → 清洗 → `INSERT` 新库。不连接老代码。

## 5. 技术栈 ⚙️

沿用你熟悉的栈，降低重做风险；只把“组织方式”做干净。

- **后端**：Java 17 + Spring Boot 3 + MyBatis-Plus（老项目同款）+ MySQL 8 + Redis
- **前端（用户端）**：Vue 3 + Vite + Pinia
- **后台（管理端）**：Vue 3（可与用户端同仓不同 app）
- **鉴权**：JWT（无状态）+ Redis 存刷新态/黑名单
- **部署**：Docker Compose（mysql / redis / api / web / admin / caddy）

> 如果想前后端同语言（TS 全栈，如 NestJS + Vue），长期更省心但有学习成本——本方案默认沿用 Java，要换告诉我。

## 7. 统计要看什么（analytics 域）

取代老项目手写脚本，做成后台看板。先盯这几个核心指标：

- **拉新**：每日注册数、注册来源、邀请裂变层级
- **活跃**：DAU / 留存（次日/7日）
- **行为**：热门搜索词、热门资源 Top N、搜索→转存转化率、转存成功率
- **变现**（收费后）：付费转化率、会员到期/续费、收入趋势、各套餐占比

实现方式：核心动作打 `event_log` 埋点 → 定时聚合成报表表 → 后台读报表。

## 8. 分阶段落地计划

> 原则：每个阶段都能独立跑起来、看得到东西，不憋大招。

**阶段 0 · 地基**
- 建仓库 + 目录骨架 + `.gitignore` + docker-compose（mysql/redis）
- 后端能起、连库、健康检查接口通

**阶段 1 · 用户体系（本次的新核心）**
- `user` 表 + 注册/登录/JWT
- 注册开关（开放/邀请码/关闭）
- `member_expire_at` 字段 + `isMember()`（先恒为 true）+ 付费墙总开关（先关）
- 后台能看用户列表、手动加/封人

**阶段 2 · 内容域 + 数据迁移**
- 建内容相关表 → 跑一次性迁移脚本，把老数据搬过来
- 用户端能浏览资源 / 每日更新 / 榜单

**阶段 3 · 搜索域**
- 移植聚合搜索（Gying / SeedHub / PanSou / Flowus），重新组织进 search 域
- 用户端能搜

**阶段 4 · 转存域**
- 网盘账号管理 + 一键转存（百度/夸克/迅雷）+ 离线任务
- 接 `usage_log`，把“转存”挂到将来的付费墙后（现在开放）

**阶段 5 · 运营 + 统计**
- 敏感词/广告过滤、投稿/求片
- 埋点 + 运营看板

**阶段 6 · 计费**
- `plan` / `redeem_code` + 卡密核销 + 后台发码（站外聚发货等收款）
- 打开付费墙总开关；**不做**主站支付接入

## 8.5 同类项目参考（借鉴架构，勿抄代码）

> ⚠️ 这些多为“仅供学习/请勿盈利”的开源项目。**可借鉴架构与产品思路，商用变现时代码须自研。**

| 项目 | 形态 | 技术栈 | 借鉴点 |
|---|---|---|---|
| **CloudSaver** (jiangrui1994) | 搜索+转存+多用户 | Vue3+TS / Express / SQLite / JWT | 与本项目最像；**注册码控制注册**、管理员/普通用户分权、一键转存交互 |
| **爱盼 aipan** (unilei) | 搜索+后台管理 | Nuxt3 全栈 / PostgreSQL / Prisma / JWT | 干净的单仓全栈结构 `server/`+`pages/`+`prisma/`；后台/账号体系 |
| **PanSou** (fish2018, 13k★) | 纯搜索 API | Go，插件化多源 | **搜索源做成可插拔插件**、并发/智能排序/分类、缓存设计 |
| **PanHub** | 纯搜索 | CF Workers | 轻量部署思路（快速结果→深度结果分段返回） |

**关键结论**：
- 这些项目**都没有“付费会员订阅”体系** → 会员/计费是本项目的**差异化**，需自研，无现成可抄。
- 搜索域采用 PanSou 式**插件化**：每个源（Gying/SeedHub/PanSou/Flowus…）是独立插件，加源不动主干。
- 注册控制借鉴 CloudSaver：除“开放/邀请码/关闭”三档外，可用**注册码**区分被注册者身份。
